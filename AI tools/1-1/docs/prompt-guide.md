# 프롬프트 구조와 운영 설계 — 평가 #8, #9, #11, #12, #15~#19

## 1. 시스템·유저·템플릿 프롬프트 구분
| 유형 | 목적 | 예시 | 적용·우선순위 |
|---|---|---|---|
| 시스템 지침 | 장기간 유지할 역할·금지·출력 원칙 | "너는 PR Guardian이다. 제공된 코드만 근거로 판단한다." | 실제 시스템 메시지로 설정 시 사용자 지시보다 우선 |
| 사용자 프롬프트 | 이번 작업과 현재 요구사항 지정 | "이 UserProfileView를 리뷰해 줘. 닉네임 3~15자" | 시스템 지침 범위 안에서 현재 과업 지정 |
| 입력 템플릿 | 매번 동일한 구조로 정보 수집 | `input-template.md`의 JSON | **별도 권한 계층이 아님**. 사용자 메시지에 포함되는 양식 |

**중요:** 이전 실험에서 '시스템 프롬프트'라 부른 내용은 실제 시스템 역할로 설치한 것이 아니라 **사용자 대화에서 지시한 텍스트**였다. 실제 시스템 메시지와 동일한 우선순위를 갖는다고 주장하지 않는다.

## 3. v1 → v2 실제 변경 문장 및 이유
| v1 핵심 규칙 | v2 개선 문장 | 변경 이유 |
|---|---|---|
| "불확실한 내용은 확인 필요라고 명시" | "사실은 확인됨, 환경 의존 영향은 가능성, 자료 부족은 확인 필요" | 확인 수준 세분화 |
| "요구사항에 맞춰 검토" | "최신 사용자 요구사항을 현재 기준으로 적용하되 변경 이전과 유지 조건을 구분" | 2~20 → 3~15 변경 대응 |
| 반복 입력에 관한 명시 규칙 없음 | "동일 코드와 동일 요구사항에는 핵심 판단과 심각도 기준을 일관되게 적용" | 반복 질문 일관성 강화 |
| "필요하면 최대 3개 질문" | "판단할 수 없으면 최대 3개 질문, 확인 가능한 부분 리뷰 제공" | 정보 부족 시 작업 중단 최소화 |
| "Critical/High/Medium/Low로 구분" | "Critical=중대한 무단 접근, High=주요 검증 누락, Medium=예외·무결성, Low=경미한 문제" | 심각도 기준 통일 |
| "실행하지 않았다면 실행했다고 주장하지 않음" | "정적 분석·실행·미확인을 명시" | 검증 수준의 오해 방지 |

**변경 성격:** STEP 4에서 뚜렷한 실패가 발견돼 수정한 것이 아니라, 향후 운영을 위한 **예방적 강화**다. v2 재실행 결과는 아직 없다. 전체 v2 본문은 `system-design.md` 참고.

## 4. 환각의 정의 및 창의성과 구분
**환각:** 실제 근거가 없거나 근거와 모순되는데도 사실로 제시하는 출력.
- 환각 예: 코드가 `AllowAny`인데 "IsAuthenticated로 보호된다"고 단정
- 창의적 제안: "별도 Profile 모델을 도입하는 방안을 고려할 수 있다" — **제안으로 명시**했다면 환각 아님
- 가정: "JWT를 사용한다면..." — 조건부임을 분명히 하면 환각 아님
- 미확인: DB 고유성 충돌의 정확한 HTTP 응답은 실행·설정에 따라 달라질 수 있음

## 5. 환각 Pass / A / B / Fail 판정 기준
| 판정 | 체크리스트 |
|---|---|
| **A (Pass)** | 코드·요구사항과 일치, 코드 근거 인용, 미확인 사항 구분, 실행 여부 정확 |
| **B (Pass, 보완 권장)** | 핵심 사실 정확하지만 근거 인용·불확실성 표시 일부 미흡 |
| **Fail** | 코드에 없는 사실 단정, 요구사항 반대로 해석, 실행하지 않은 테스트를 실행했다고 주장, 핵심 사실 오답 |

**판정 순서:** ① 질문별 기대 사실 명시 → ② 코드 위치 대조 → ③ 주장·근거·조건부 표현 확인 → ④ A/B/Fail 기록. 하나라도 핵심 사실을 잘못 단정하면 Fail로 분류한다.

## 6. 무료 모델 품질 유지 운영안 (제안, 미실행)
- 프롬프트: 고정 v2와 동일 입력 JSON을 사용하고 모델 변경 시 샘플 PR 재평가
- 검수: PR마다 Critical/High 항목은 사람이 확인; 주 1회 5건 샘플 재평가
- 지표: 핵심 취약점 탐지율, 잘못된 지적 비율, 형식 준수율, 확인 필요 표시율, 사람 수정률
- 트리거: 필수 보안 문제 미탐지 또는 잘못된 사실 단정 시 해당 리뷰 수동 검토 및 프롬프트 회귀 테스트
- 무료 모델의 가용성·버전·쿼터는 변동 가능하므로 실행 당시 조건을 로그에 보존

## 7. 정책 변경 대응 절차 (제안, 미실행)
1. **접수:** 정책 버전, 변경 일시, 이전/신규 값, 유지 조건 기록
2. **테스트:** 경계값과 기존 회귀 테스트 작성 (예: 2,3,15,16자)
3. **프롬프트 갱신:** 현재 유효한 정책만 리뷰 기준에 반영하고 변경 내역 별도 보존
4. **롤아웃:** 샘플 PR에 먼저 적용하고 사람 검수 후 전체 적용
5. **모니터링:** 1주 동안 정책 혼동 건수와 오탐률 확인; 오류 시 이전 버전 복귀

## 8. 문맥 끊김 대응 (제안, 미실행)
- **세션 요약:** PR명, 코드 해시, 요구사항 버전, 미해결 질문, 결정된 심각도 요약
- **체크포인트:** 5턴마다 '현재 적용 조건'과 근거 표 갱신
- **재프레이밍:** 새 세션 첫 메시지에 최신 요구사항과 원본 코드 재첨부, 이전 대화 추측 금지
- **검사:** 변경 전후의 닉네임 길이를 질문해 최신 3~15자를 답하는지 확인

## 9. 작업 단위 분할 (제안, 미실행)
| 단위 | 목표 | 입력/산출물 | 검사 기준 |
|---|---|---|---|
| A 요구사항 추출 | 현재 정책 확정 | PR 설명 → 조건 목록 | 변경/유지 조건 구분 |
| B 코드 근거 수집 | 취약 지점 찾기 | 코드 → 파일·라인·근거 | 실제 코드에 존재 |
| C 위험 평가 | 심각도 부여 | 근거 → 영향·등급 | 등급 기준 일관성 |
| D 수정안 | 개발자 조치 제공 | 문제 → 수정 방향 | 적용 가능·부작용 검토 |
| E 검수 | 환각·누락 방지 | 리뷰 초안 → 최종 판정 | A/B/Fail 체크리스트 |

각 단위는 목표·입력·산출물·검사 기준을 충족한 뒤 다음 단계로 넘긴다.
